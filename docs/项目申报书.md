## 1. 项目名称

moonmedic —— MoonBit 实现的 Kubernetes 确定性故障证据引擎

## 2. 项目简介

Kubernetes 里最常见的故障不是"Pod 崩溃",而是"Pod 根本没有被创建":配额耗尽、LimitRange 拒绝、准入拦截发生时,`kubectl get pods` 只会说"没有 Pod"。moonmedic 用 MoonBit 实现了一个确定性故障证据引擎:从 Deployment、ReplicaSet、ResourceQuota、Events 这些仍然存在的对象中重建故障因果链,每条结论绑定对象与字段级证据;诊断不依赖 LLM,支持离线回放,可选的 LLM 叙述层只做归纳、不产生根因。全部 MoonBit 实现(native 后端,零 C stub),已在真实 RKE2 集群上完成端到端验证。

## 3. 项目方向,通用性说明

方向:Kubernetes 运维诊断工具(AI 应用,AI 仅作可选叙述层)。

通用性:三层可复用。① `ClusterSnapshot` 快照 IR:把 Pod、Deployment、ReplicaSet、Event、ResourceQuota、LimitRange 归一为声明式 JSON,实时集群、kubectl 导出、录制文件都只是它的来源;② 确定性诊断内核:UID 对象图遍历、K8s Quantity 算术(10/500m/64Mi/4Gi/2G/1e3)、约束回放、因果链,零 kubemoon/零 LLM/零网络依赖(CI 强制检查);③ 可回放评测语料:快照 + 期望诊断 + golden 断言,可复用于数据库巡检、日志分析、CI 失败归因等其它运维场景。

## 4. 预期使用场景(3 个,均已在真实 RKE2 集群注入验证)

**场景一|配额超限导致 Pod 未创建**:发布后 Deployment 期望 2 个副本,但一个新 Pod 都没有。引擎沿 UID 对象图取证:ReplicaSet `ReplicaFailure=True`、`FailedCreate` 事件("exceeded quota: zero-pods, requested: pods=1")、ResourceQuota `used=0 / hard=0` → 根因 quota_exceeded,并数值计算出修复建议("还差 2 个;将 hard 提高到 ≥2")。

**场景二|配额只允许部分副本创建**:配额 pods=1、期望副本 2,一个 Pod 创建成功、另一个被拒。报告缺失副本数为 1 而非 2,配额建议考虑已有使用量。

**场景三|LimitRange 拒绝与配额耗尽的区分**:容器内存 256Mi 超过 LimitRange max 64Mi 时命中 limitrange_reject,而 quota_exceeded 正确缺席——避免把准入拒绝误报为配额问题。

## 5. 拟实现的核心功能

- `ClusterSnapshot` 快照 IR + 数据完整性状态(Available/Empty/Unavailable/Truncated):"API 读取失败"不得当作"空列表",不可用时相关结论自动降级;
- UID 对象图归属隔离(跨工作负载 Pod 不污染目标计数)与 K8s Quantity 算术;
- 13 条诊断规则 + 诊断分层(root_cause / mechanism / symptom / insufficient)+ 结构化 Evidence 引用(对象、字段路径、观测值);
- CLI:`--deployment`、`--json`、`--snapshot <file>` 离线回放(无集群/无网络/无 LLM);
- 评测集:真实集群注入 5 场景 + golden 断言,`run-all.sh` 离线 5/5 通过;
- 51 个单元测试 + CI(fmt --check / check / test,并强制核心包不依赖 kubemoon 与 LLM)。
